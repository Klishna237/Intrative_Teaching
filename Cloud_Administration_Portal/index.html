01. NIST SP 800-145 Cloud Definition, Essential Characteristics & Service Tiers

Cloud computing is formally defined by the National Institute of Standards and Technology (NIST SP 800-145) as a model for enabling ubiquitous, convenient, on-demand network access to a shared pool of configurable computing resources (e.g., networks, servers, storage, applications, and services) that can be rapidly provisioned and released with minimal management effort or service provider interaction.

The 5 NIST Essential Characteristics: PRRES

Every true cloud deployment must satisfy all five criteria:
• P – Pooling of Resources: Multi-tenant pooling where physical hardware is dynamically assigned and reassigned according to consumer demand without client visibility into physical location.
• R – Rapid Elasticity: Capabilities can be elastically provisioned and released to scale rapidly outward and inward commensurate with demand.
• R – Resource Measurement (Measured Service): Resource usage is monitored, controlled, and reported, providing transparency (metered pay-as-you-go).
• E – Essential On-Demand Self-Service: A consumer can unilaterally provision computing capabilities (CPU, storage) automatically without requiring human interaction with the cloud service provider.
• S – Standard Broad Network Access: Capabilities are accessible over high-bandwidth networks via standard mechanisms (HTTP/HTTPS REST APIs) from diverse client platforms (laptops, phones, workstations).

IaaS (Infrastructure as a Service) Physical datacenter facilities, HVAC, physical servers, host virtualization hypervisors, and physical network fabric. Operating system installation, kernel patching, network configuration (VPC/Firewalls), database engines, runtime, and application code. Amazon EC2, Amazon EBS, Amazon VPC
PaaS (Platform as a Service) Physical hardware, virtualization, operating system licensing, kernel patching, runtime environments, and capacity autoscaling. Deploying application code, configuring environment variables, database schema tuning, and data backups. AWS Elastic Beanstalk, AWS Lambda, Amazon RDS

02. Virtualization Physics: Type-1 vs Type-2 Hypervisors & CPU VMX Extensions

Virtualization is the foundational technological enabler of cloud computing, decoupling operating systems and application runtimes from underlying physical silicon through hardware-assisted virtualization instruction set extensions.

Hypervisor Category Underlying Host Layer Latency Overhead I/O Interception Mechanism Enterprise Cloud Deployments
Type-1 Bare-Metal Executes directly on bare-metal physical hardware; acts as its own lightweight operating system Ultra-low (~1-2% virtualization tax) Direct hardware CPU instruction scheduling via Intel VT-x / AMD-V VMX root mode AWS Nitro Hypervisor, VMware ESXi, Microsoft Hyper-V, KVM
Type-2 Hosted Executes as an application process inside a full host operating system (e.g. Windows/macOS/Linux) High (~10-25% virtualization tax due to double scheduling) Guest I/O requests must traverse guest kernel → hypervisor → host OS kernel → physical silicon Oracle VirtualBox, VMware Workstation, Parallels Desktop
Silicon Architecture: Intel VT-x VMX Root vs Non-Root Execution

Legacy x86 architectures suffered from Popek-Goldberg virtualization virtualization holes where sensitive CPU instructions (such as `POPF` or `CLI`) executed silently without trapping when called from Ring 1. In 2005, Intel introduced hardware-assisted virtualization extensions adding two orthogonal operating modes:

  • VMX Root Operation: The privileged execution mode reserved for the bare-metal hypervisor (VMM). The hypervisor possesses unrestricted access to hardware control registers (`CR0`, `CR3`, `CR4`) and MSRs.
  • VMX Non-Root Operation: The execution mode where guest virtual machines execute. Even if the guest OS runs at internal Ring 0, sensitive instructions or page-table modifications automatically trigger a VM-Exit, trapping back into the VMX root hypervisor. The hypervisor inspects the Virtual Machine Control Structure (VMCS), emulates or validates the operation, and executes a `VMRESUME` instruction to transition execution back to the guest.
  • Second Level Address Translation (SLAT / EPT): Hardware Extended Page Tables (EPT) maintain guest-physical to host-physical memory translations directly inside the CPU Memory Management Unit (MMU) TLB cache, eliminating hypervisor shadow page table traps and accelerating memory access by 40%.

03. AWS Global Infrastructure Topology: Regions, Availability Zones & Edge PoPs

The Amazon Web Services global cloud infrastructure is architected as a multi-tier, fault-isolated hierarchy engineered to guarantee sub-millisecond latencies, geographic disaster tolerance, and high regulatory compliance.

AWS Global Infrastructure Fault-Isolation Hierarchy
TIER 1 • AWS GEOGRAPHIC REGIONS (e.g. us-east-1, eu-west-1, ap-south-1)
Isolated geographic clusters separated by hundreds of kilometers • Completely independent power, water, cooling, and regulatory boundaries • Interconnected via private redundant 100GbE DWDM dark fiber backbone
⇕ Private Encrypted Low-Latency Fiber Interconnect (< 2 ms Round-Trip Time) ⇕
TIER 2 • AVAILABILITY ZONES (AZs: us-east-1a, us-east-1b, us-east-1c)
Each AZ comprises one or more discrete physical datacenters • Independent flood plains, separate electrical utility sub-stations, and redundant diesel generators • Physical separation prevents localized disaster contagion
⇕ Anycast Border Gateway Protocol (BGP) Routing ⇕
TIER 3 • EDGE NETWORK (600+ CloudFront Points of Presence & Regional Edge Caches)
Global Edge Locations positioned adjacent to Tier-1 Internet Service Providers • Terminates TLS sessions at the edge • Caches static S3/Web assets • Mitigates DDoS via AWS Shield
High-Availability Tenet: AZ Independence & AZ ID Mapping

Availability Zones within a single Region are physically located within 100 kilometers (60 miles) of each other to maintain ultra-low round-trip latency (<2 milliseconds), allowing synchronous Multi-AZ database replication (e.g. Amazon Aurora). However, they are located on separate geographic fault lines and flood plains.

AZ ID Randomization: To ensure even resource distribution across physical buildings, AWS randomly maps letter designations (`us-east-1a`, `us-east-1b`) for each AWS Account. Account A's `us-east-1a` might physically map to Account B's `us-east-1c`! To align physical resources across multiple AWS corporate accounts, engineers must coordinate via the immutable AZ ID (e.g. `use1-az1`).

04. The AWS Shared Responsibility Model: Security OF the Cloud vs Security IN the Cloud

Information security and compliance in AWS is a shared partnership between the cloud provider and the subscribing customer. Understanding the demarcation boundary across IaaS, PaaS, and SaaS tiers is paramount to preventing security breaches and regulatory compliance audit failures.

Domain Layer Responsible Party Specific Operational Scope
Customer Data & Workloads CUSTOMER (Security IN the Cloud) Data encryption (in-transit via TLS, at-rest via KMS), IAM user credentials, MFA enforcement, database schemas, application code vulnerability patching.
Operating System & Network Configuration CUSTOMER (IaaS EC2) / AWS (PaaS RDS) In EC2: Customer must patch OS kernel, configure Windows Defender / iptables, and define Security Group egress/ingress rules. In RDS: AWS manages OS patching.
Host Virtualization & Hypervisors AWS (Security OF the Cloud) Nitro Hypervisor microcode updates, CPU VMX isolation, memory page wiping between tenant allocations, host disk zero-fill on detachment.
Physical Facilities & Infrastructure AWS (Security OF the Cloud) Biometric datacenter perimeter access, CCTV monitoring, backup diesel generators, HVAC climate control, hardware destruction (DoD 5220.22-M disk shredding).
The Enterprise Misconception: The "AWS Fixes My Backups" Trap

A catastrophic mistake made by novice cloud engineers is assuming that because an application runs on AWS, it is automatically backed up, resilient to ransomware, and immune to configuration errors. AWS guarantees that the physical hard drives and hypervisors function. If an administrator accidentally issues `DROP DATABASE production;` or leaves an S3 bucket publicly readable (`s3:PutBucketAcl: public-read`), this is 100% the customer's failure under the Shared Responsibility Model. AWS does not inspect customer data or reverse customer-initiated API deletions.

05. Cloud Economics: CapEx vs OpEx & The 6 Advantages of Cloud Computing

Transitioning enterprise IT infrastructure from on-premises datacenters to hyperscale public cloud providers transforms corporate balance sheets by replacing rigid capital expenditure depreciation cycles with agile operational expenditure consumption models.

The 6 Advantages of Cloud Computing

1. Trade Capital Expense for Variable Expense: Pay only when computing resources are consumed (OpEx) instead of investing millions upfront in physical datacenters and unboxed servers (CapEx).
2. Benefit from Massive Economies of Scale: Because AWS aggregates hundreds of thousands of customers, it achieves higher purchasing power, translating into 130+ continuous price reductions over historical operations.
3. Stop Guessing Capacity: Eliminate expensive idle hardware provisioned for peak loads or disastrous server crashes when traffic surges past capacity limits. Scale instances up and down dynamically.
4. Increase Speed and Agility: New IT resources are accessible to software developers in seconds with single API calls rather than taking 12 to 16 weeks for server delivery and rack mounting.
5. Stop Spending Money Running and Maintaining Datacenters: Focus software engineering talent on differentiated business applications rather than "undifferentiated heavy lifting" (power cables, cooling chillers, physical security).
6. Go Global in Minutes: Deploy applications in multiple AWS Regions worldwide with clicks, providing lower latency and superior customer experience with minimal cost.

07. Unit 1 Short Conceptual Questions (5 High-Yield Sets)

Targeted explanations of core cloud concepts, virtualization physics, and infrastructure demarcation.

Q1 Contrast Type-1 (Bare-Metal) and Type-2 (Hosted) hypervisors regarding architecture, latency overhead, and enterprise cloud fitness.

Type-1 (Bare-Metal / e.g. AWS Nitro, ESXi, KVM): Installs directly onto bare physical silicon. It interacts directly with CPU VMX root mode and memory controllers with near-zero virtualization overhead (~1-2%). Because there is no intermediary host OS, it delivers deterministic line-rate performance and strict tenant isolation, making it the mandatory architecture for public cloud datacenters.

Type-2 (Hosted / e.g. VirtualBox, VMware Workstation): Installs as a user application on top of an existing host operating system (Windows/macOS). Every I/O request must be translated through the host OS kernel and scheduler, incurring a 10-25% latency tax. It is suitable only for local developer testing, not production cloud multi-tenancy.

Q2 Explain how Intel VT-x hardware virtualization extensions solved the historic Popek-Goldberg x86 virtualization trap.

In legacy x86 CPUs, 17 sensitive instructions (such as `POPF`, `PUSHF`, `CLI`) failed to generate an interrupt when executed in unprivileged Ring 1; instead, they failed silently or behaved unpredictably, violating Popek-Goldberg virtualization rules.

Intel VT-x resolved this by introducing two hardware operating modes: VMX Root (for the hypervisor) and VMX Non-Root (for guest VMs). Whenever a guest VM attempts to execute a sensitive instruction or modify control registers, the hardware CPU automatically forces a VM-Exit, suspending the guest and transferring execution to the VMX root hypervisor. The hypervisor inspects the Virtual Machine Control Structure (VMCS), handles the operation securely, and issues `VMRESUME` to continue execution.

Q3 Detail the geographic and physical fault-isolation architecture separating AWS Regions and Availability Zones.

Regions: Separate geographic clusters located hundreds or thousands of kilometers apart (e.g. `us-east-1` in Virginia vs `ap-south-1` in Mumbai). Each Region is completely autonomous with independent power grids, water supplies, and regulatory boundaries, interconnected via dedicated private dark fiber.

Availability Zones (AZs): Within a Region, each AZ consists of one or more physical datacenters separated by up to 100 km on distinct flood plains and separate electrical utility substations. Round-trip fiber latency is maintained below 2 milliseconds, allowing synchronous data mirroring while ensuring a localized catastrophe (e.g. transformer fire or localized flooding) cannot compromise sibling AZs.

Q4 Explain the demarcation boundary of the AWS Shared Responsibility Model across IaaS (EC2) vs PaaS (RDS) vs SaaS (QuickSight).

IaaS (EC2): AWS manages the physical facilities, host servers, and hypervisors. The customer is responsible for guest OS installation, OS security patching, firewall rules (Security Groups), middleware, and application data.

PaaS (RDS): The demarcation shifts upward. AWS manages the physical host, hypervisor, and the guest OS kernel patching and automated backups. The customer is responsible only for database configuration parameters, schema architecture, indexing, and user credential management.

SaaS (QuickSight): AWS manages the entire stack from physical hardware up through application code. The customer is solely responsible for user account administration and data access governance.

Q5 How does shifting from Capital Expenditure (CapEx) to Operational Expenditure (OpEx) transform business agility?

CapEx (Traditional): Requires massive upfront cash outlays to purchase physical servers, SAN storage, and networking switches, followed by 3-to-5 year accounting depreciation cycles. Infrastructure planning relies on guessing peak capacity 18 months in advance, resulting in either expensive idle hardware or catastrophic capacity shortages during unexpected surges.

OpEx (Cloud): Treats computing as a metered operational utility. Infrastructure costs correlate 1:1 with real business revenue and customer traffic. Organizations eliminate stranded assets, experiment with new technologies with zero upfront risk, and scale resources up or down instantaneously.

  • Why Multi-Region Cannot Guarantee RPO = 0: The physical speed of light in fiber optic glass is ~200 km/millisecond. Silicon Architecture: What Exactly is a vCPU?

On x86 Intel and AMD platforms, 1 vCPU equals 1 hardware execution thread (Hyper-Thread) on a physical multi-core CPU. A physical core with Simultaneous Multithreading (SMT) provides 2 vCPUs. For example, a `c7i.2xlarge` instance provides 8 vCPUs, which maps to 4 physical hyper-threaded CPU cores. On ARM-based AWS Graviton3/4 processors, SMT is disabled; therefore, 1 vCPU represents an entire dedicated physical CPU core, delivering deterministic performance with zero inter-thread L1 cache eviction contention!

An Auto Scaling Group (ASG) maintains application availability by enforcing Minimum, Maximum, and Desired capacity limits:

14. Serverless Computing: AWS Lambda, Firecracker MicroVMs & Event-Driven Architecture

Serverless computing abstracts server provisioning, operating system maintenance, and capacity capacity management completely. Application code executes strictly in response to discrete triggers, with billing calculated in 1-millisecond increments.

Silicon Architecture: How Firecracker MicroVMs Boot in 5 Milliseconds

Legacy virtual machines (such as QEMU) emulated complex legacy PC hardware (floppy drives, IDE controllers, PCI buses), requiring 30 to 60 seconds to boot. To make serverless scalable, AWS built Firecracker—an open-source Virtual Machine Monitor (VMM) written in Rust utilizing the Linux Kernel-based Virtual Machine (KVM):

  • Stripped Device Model: Firecracker strips away all legacy PC hardware emulations, providing only a minimal serial console, a block device, a network device, and a hardware cryptographic TRNG.
  • Blazing Fast Boot Time: A Firecracker MicroVM boots a guest Linux kernel in under 5 milliseconds while consuming only 5 MiB of RAM!
  • Multi-Tenant Security: Unlike Docker containers which share the host kernel (where a single kernel privilege escalation compromises all tenants), each Lambda function executes inside its own hardware-isolated Firecracker MicroVM with dedicated CPU non-root isolation and seccomp-bpf system call filters.

Q1 Contrast Application Load Balancers (ALB) and Network Load Balancers (NLB) regarding OSI layer, routing criteria, and latency profiles.

ALB (Layer 7): Inspects HTTP/HTTPS application payloads. Routes traffic based on host headers, URL paths (e.g. `/api` vs `/checkout`), query parameters, and HTTP methods. Terminates TLS and supports Server Name Indication (SNI). Latency is ~5-15 ms due to deep packet inspection.

NLB (Layer 4): Operates strictly at the Transport layer (TCP/UDP). Does not touch application payloads. Capable of processing tens of millions of requests per second with sub-millisecond latency. Provides static Elastic IPs per AZ and supports client IP preservation without modifying HTTP headers, making it ideal for gaming, trading, and non-HTTP protocols.

Q2 Explain how the AWS Nitro System completely removes the performance and security overhead of the legacy Xen Dom0 management VM.

In legacy cloud architectures (Xen), a privileged management virtual machine (Dom0) executed alongside customer guest VMs, consuming up to 30% of host CPU and memory to handle networking encapsulation, disk I/O virtualization, and telemetry monitoring.

The AWS Nitro System physically offloads these responsibilities onto dedicated PCIe ASIC cards (Nitro Card for VPC, Nitro Card for EBS, Nitro Security Chip). The host CPU no longer runs Dom0 or heavy virtualization daemons; it runs a stripped-down microvisor that merely allocates memory and schedules CPU threads. This delivers nearly 100% of host silicon to customer instances and eliminates hypervisor jitter.

Q3 Detail the operational lifecycle of an EC2 Spot Instance termination: notification, state draining, and re-allocation strategies.

When demand for On-Demand capacity surges, AWS reclaims spare Spot compute capacity. The process follows a strict 2-minute timeline:

  1. 2-Minute Warning: AWS issues an EC2 Spot Instance Interruption Notice accessible via instance metadata (`http://169.254.169.254/latest/meta-data/spot/instance-action`) and Amazon EventBridge.
  2. Graceful Draining: Workload agents intercept the event, deregister the instance from load balancers, finish active in-flight requests, and flush state or checkpoint data to Amazon S3 or DynamoDB.
  3. Mitigation Strategy: Deploy Spot Fleets using the `price-capacity-optimized` allocation strategy across multiple instance families and multiple AZs to ensure auto-replacement occurs in healthy pools.
Q4 How does AWS Firecracker achieve microVM isolation in under 5 milliseconds compared to standard Docker container runtimes?

Standard Docker containers provide process-level isolation sharing the host Linux kernel. If a container executes a malicious kernel exploit (e.g. dirty COW), all sibling containers on the host can be breached.

Firecracker is a lightweight Virtual Machine Monitor written in Rust that creates full hardware-isolated virtual machines using Linux KVM. Firecracker strips all legacy PC peripheral emulations (USB, ACPI, IDE), leaving only a minimal serial port, virtio block, and virtio net device. This minimal device model boots a full Linux kernel in <5 ms inside a hardware VMX non-root sandbox with 5 MiB memory footprint, combining the security of hardware virtualization with the speed of containers.

Q5 Differentiate Cluster, Spread, and Partition EC2 Placement Groups from an infrastructure reliability perspective.

Cluster: Packs instances close together inside a single Availability Zone on the same network spine. Delivers high throughput (100 Gbps) and ultra-low latency for HPC and big data clusters, but carries higher risk (AZ failure impacts all nodes).

Spread: Strictly places each instance on a separate physical server rack with distinct power and network sources (maximum 7 instances per AZ). Used for mission-critical replicated pairs (e.g. primary/standby SQL databases).

Partition: Divides the placement group into logical partitions; instances in one partition do not share hardware racks with other partitions. Tailored for distributed topologies like Apache Cassandra, Kafka, and HDFS.

20. S3 Multipart Uploads, Lifecycle Rules, Versioning & Object Lock

Managing petabyte-scale object lifecycles requires programmatic automation to optimize storage costs, ensure immutable regulatory compliance, and accelerate network ingest of massive multi-gigabyte payloads.

Engineering Mechanics: The S3 Multipart Upload Architecture

For any object exceeding 100 MB (and mandated for objects > 5 GB up to the 5 TB single-object ceiling), engineers must utilize the S3 Multipart Upload API:

  • Parallel Transmission: The client chunks the file into parts (from 5 MB to 5 GB each). Parts 1 through \(N\) are transmitted concurrently over independent TCP streams, saturating available network bandwidth.
  • Fault Tolerance & Resiliency: If Part 42 experiences a network timeout or packet corruption, only that single 10 MB chunk is retried rather than restarting the entire 500 GB upload!
  • ETag Mathematical Verification: Standard S3 objects have an ETag equal to the hex MD5 checksum of the file. In a multipart upload, the ETag represents the MD5 hash of the concatenated binary MD5 hashes of each individual part, suffixed by the part count (e.g. `d41d8cd98f00b204e9800998ecf8427e-45`).

Targeted explanations of object vs block storage, multi-part parallel ingestion, and distributed filesystem semantics.

Q1 Contrast Object Storage (Amazon S3) and Block Storage (Amazon EBS) regarding addressing, update mechanics, and operational targets.

Object Storage (S3): Treats data as complete, indivisible objects referenced by a URL key within a flat namespace. Supports rich customizable metadata. Modifying a single byte requires rewriting the entire object. Scales infinitely to exabytes and is accessed over HTTP/HTTPS REST APIs.

Block Storage (EBS): Divides storage into raw 512-byte or 4KB sectors (blocks) without metadata. Operating systems format volumes with native filesystems (NTFS/ext4) and can alter individual bytes directly with sub-millisecond random I/O latency. Bound to a single instance in a specific AZ; ideal for transactional database engines and OS root drives.

Q2 Explain how S3 Multipart Upload achieves high throughput and network resiliency for multi-gigabyte video files.

Parallelization: S3 Multipart Upload chunks large files into parts (5 MB to 5 GB each). Instead of serial upload over a single TCP connection, client workers upload dozens of chunks concurrently over parallel sockets, saturating high-bandwidth connections.

Failure Isolation: Over unstable long-haul networks, single-stream uploads frequently drop at 98%, forcing a full restart. With Multipart Upload, if a single chunk fails due to packet loss, only that specific chunk is retried. S3 verifies individual chunk MD5 hashes, reassembles the file into a unified object, and generates a composite multipart ETag.

Q3 Detail the operational difference between S3 Object Lock Compliance Mode and Governance Mode.

Governance Mode: Protects objects from accidental deletion by standard users. However, users granted the special `s3:BypassGovernanceRetention` IAM permission can alter retention periods or delete versions if authorized.

Compliance Mode: Enforces strict Write-Once-Read-Many (WORM) immutability. No user in the organization, including the AWS Account Root User, can delete the object or decrease its retention period until time expires. AWS Support cannot bypass it. Mandated for legal and financial compliance (SEC Rule 17a-4).

Q4 How does Amazon EBS gp3 decouple IOPS and throughput from volume capacity, and why is this financially advantageous over gp2?

Under legacy `gp2`, IOPS were locked to size at 3 IOPS per GiB. A database requiring 3,000 IOPS forced the customer to provision a 1,000 GiB volume, resulting in massive wasted spend on unneeded storage capacity.

Under `gp3`, every volume receives 3,000 IOPS and 125 MB/s baseline throughput for free. If higher performance is needed, administrators can independently provision up to 16,000 IOPS and 1,000 MB/s on a small 50 GiB disk. This decoupling allows precise workload tailoring and cuts average EBS monthly costs by up to 20-40%.

Q5 Contrast Amazon EFS and Amazon FSx for Lustre regarding protocol, architecture, and optimal computing workloads.

Amazon EFS: Serverless NFSv4 filesystem built for general-purpose Linux workloads. Synchronously replicates across multiple Availability Zones, offering high durability and automatic growth to petabytes. Ideal for web content management (WordPress), developer home directories, and container shared storage.

Amazon FSx for Lustre: High-performance parallel filesystem designed for compute-heavy batch workloads. Provides sub-millisecond latencies, hundreds of gigabytes/second throughput, and millions of IOPS. Links directly to S3 data lakes to ingest datasets for High-Performance Computing (HPC), machine learning training, and financial simulations.

Scenario 01 Storage Incident Triage: Lazy-Loading Latency Spike on Newly Restored 10TB EBS Database Volume

Incident Description: During a disaster recovery drill, a systems team restores a 10TB production PostgreSQL database from an EBS snapshot onto a brand-new `gp3` volume. When launching the database, query latencies spike to 3,500 milliseconds (normally 4 ms), database connections pool and time out, and disk queue depth exceeds 200 despite provisioning 12,000 IOPS.

Root Cause Analysis & Resolution:

  1. The Lazy-Loading (Hydration) Penalty: EBS snapshots are stored in Amazon S3. When an EBS volume is created from a snapshot, storage blocks are not pre-copied to the physical SAN drives; instead, metadata pointers are created instantly. When the database reads a disk block for the first time, the block must be pulled over the network from S3 ("lazy loading"), causing an initial 50-100 ms latency spike per block!
  2. Immediate Manual Pre-Warming: To force block hydration immediately without waiting for database queries to hit cold blocks, execute a raw sequential read across the entire volume in Linux:
    sudo dd if=/dev/xvdf of=/dev/null bs=1M status=progress
    This forces the hypervisor to fetch every block from S3 immediately.
  3. Architectural Permanent Fix: Enable EBS Fast Snapshot Restore (FSR) on critical database snapshots. FSR pre-warms all volume blocks into the EBS storage tier in advance, eliminating the hydration penalty completely and delivering 100% full provisioned IOPS from the very first second of restoration.

28. Amazon Virtual Private Cloud (VPC) Architecture & The 5 Reserved IPs

An Amazon VPC is a logically isolated software-defined virtual network dedicated to an AWS account. It mirrors a traditional physical corporate network, operating within an overlay network using encapsulation protocols executed directly on the AWS Nitro hardware fabric.

Subnet Usable IP Math: The 5 Reserved IPs per Subnet

In standard on-premises networking, only 2 addresses are subtracted from a subnet (Network ID and Directed Broadcast). In AWS VPC, exactly 5 IP addresses are reserved in every subnet and cannot be assigned to instances:

  • `.0` – Network Address: The base CIDR network identifier.
  • `.1` – VPC Local Router: Assigned to the default gateway router virtual interface.
  • `.2` – Amazon Route 53 DNS Resolver: The base of the VPC CIDR plus 2 (e.g. `10.0.0.2` in `10.0.0.0/16`), providing AmazonProvidedDNS.
  • `.3` – Future AWS Reservation: Reserved by AWS for future protocol extensions.
  • `.255` – Network Broadcast Address: Although AWS does not support broadcast routing, the top address is reserved to maintain standard TCP/IP compatibility.
  • Capacity Formula: For a \(/24\) subnet (\(2^8 = 256 ext{ total}\)), usable instances = \(256 - 5 = \mathbf{251 ext{ usable IP addresses}}\).

Targeted explanations of software-defined cloud networking, firewall statefulness, and hybrid transit routing.

Q1 Explain the architectural and mathematical reason why exactly 5 IP addresses are reserved in every AWS VPC subnet.

In standard networking, only 2 addresses are reserved (Network ID and Broadcast). AWS VPC reserves exactly 5 addresses in every subnet:

  • `.0` (Network ID): Base CIDR network identifier.
  • `.1` (VPC Local Router): Default gateway IP virtual interface for routing off-subnet traffic.
  • `.2` (AmazonProvidedDNS): Internal recursive Route 53 DNS resolver endpoint (base + 2).
  • `.3` (Future AWS Reservation): Reserved by AWS for protocol enhancements.
  • `.255` (Broadcast Address): Reserved to preserve standard TCP/IP stack compatibility, even though AWS does not route layer 2 broadcasts.
Q2 Contrast the stateful operational behavior of Security Groups with the stateless behavior of Network ACLs.

Security Groups (Stateful): Operate at the instance ENI level. Security Groups maintain a dynamic connection state table. When an inbound rule permits a packet, return traffic is automatically tracked and allowed outbound, regardless of outbound rules. They support ALLOW rules only.

Network ACLs (Stateless): Operate at the subnet boundary. NACLs do not track connection states. Inbound and outbound traffic are evaluated as completely independent, unrelated packets. If an inbound web request is allowed on port 80/443, the administrator must explicitly configure an outbound rule allowing ephemeral ports (1024-65535) for the response to leave the subnet! They evaluate rules in numerical order and support both ALLOW and DENY rules.

Q3 What is non-transitive routing in VPC Peering, and how does AWS Transit Gateway eliminate this operational constraint?

Non-Transitive VPC Peering: If VPC A is peered with VPC B, and VPC B is peered with VPC C, traffic from VPC A cannot transit through VPC B to reach VPC C. Direct point-to-point peering requires a full mesh: \(N(N-1)/2\) peering links, which becomes unmanageable across hundreds of corporate VPCs.

AWS Transit Gateway (TGW): Functions as a centralized cloud router in a hub-and-spoke star topology. TGW supports fully transitive routing: VPCs attach to the TGW via Elastic Network Interfaces, and traffic routes seamlessly across any attached VPC, on-prem VPN, or Direct Connect connection through customizable route tables.

Q4 Contrast Gateway VPC Endpoints and Interface VPC Endpoints (AWS PrivateLink).

Gateway Endpoints: Target entries configured directly in VPC Route Tables for Amazon S3 and Amazon DynamoDB. They are completely free of charge and do not consume IP addresses in your subnets.

Interface Endpoints (PrivateLink): Provision an Elastic Network Interface (ENI) with a private IP address directly inside your subnet. They support 150+ AWS services, third-party partner SaaS endpoints, and custom microservices. Billed on an hourly endpoint fee plus per-GB data processing fees.

Q5 When is AWS Direct Connect preferred over an AWS Site-to-Site VPN, and how can they be combined for maximum availability?

When Direct Connect is Preferred: Direct Connect provides dedicated private physical optical fiber (1/10/100 Gbps) bypassing the public Internet. It is selected when workloads require deterministic, jitter-free low latency, heavy continuous multi-terabyte data transfers, or lower data egress fees.

High-Availability Architecture: The primary path routes over AWS Direct Connect. An AWS Site-to-Site VPN is configured as an automated failover backup link using BGP dynamic routing with AS-Path prepending. If a backhoe cuts the physical Direct Connect fiber, traffic automatically fails over to the IPsec VPN tunnel within seconds.

Scenario 01 Network Outage Triage: Asymmetrical Packet Drop Triggered by Missing Ephemeral Port in Custom NACL

Incident Description: A network security administrator creates a new custom Network ACL for a public web subnet. Inbound Rule 100 allows TCP Port 80, and Inbound Rule 110 allows TCP Port 443 from `0.0.0.0/0`. Outbound Rule 100 allows TCP Port 80 and 443 to `0.0.0.0/0`. Immediately after association, external web browsers report `ERR_CONNECTION_TIMED_OUT`. Pinging the web server succeeds.

Diagnostic & Engineering Analysis:

  1. The Stateless Trap: Network ACLs are completely stateless. When a client browser connects to a web server on port 443, the client's operating system allocates a temporary random source port known as an ephemeral port (typically in the range of 1024 to 65535).
  2. The Failure Point: The server receives the SYN packet (Inbound port 443 is allowed). The server generates the SYN-ACK response packet: Source Port = 443, Destination Port = 52140. When the response hits the NACL, the NACL evaluates Outbound rules. The outbound rule only allows ports 80 and 443! Because port 52140 is not allowed, the response packet is silently dropped by the default `* DENY` rule!
  3. Remediation: Add an Outbound NACL Rule: Rule 120 – ALLOW – TCP – Ports 1024-65535 – Destination: 0.0.0.0/0. Traffic immediately flows and websites load in milliseconds.

Incident Description: A fin-tech company hosts its payment API across three Availability Zones (`us-east-1a`, `us-east-1b`, `us-east-1c`) in private subnets. 38. Amazon Aurora Distributed Architecture, 4-of-6 Storage Quorum & Serverless v2

Amazon Aurora completely reimagines relational database architecture for the cloud by cleanly decoupling the SQL processing compute tier from the underlying distributed storage subsystem.

Distributed Storage Physics: The 4-of-6 Quorum Model

In traditional databases, the database engine writes full dirty pages, doublewrite buffers, and WAL logs to disk. Aurora writes only redo log records over the network to a shared, cluster-wide distributed storage fleet:

  • 6-Way Mirroring Across 3 AZs: Every 10 GB segment of database volume is replicated 6 times across 3 distinct Availability Zones (2 copies per AZ).
  • Write Quorum (4-of-6): A transaction is committed and acknowledged to the client as soon as 4 out of the 6 storage nodes acknowledge persisting the redo log. An entire Availability Zone can physically disappear, plus one additional storage node can crash, and Aurora continues writing with zero data loss!
  • Read Quorum (3-of-6): Reads require agreement from only 3 nodes. The compute head reads directly from local storage nodes; background peer-to-peer gossip algorithms repair lagging nodes asynchronously without compute intervention.
  • 15 Millisecond Read Replicas: Because all compute instances mount the exact same shared virtual storage volume, Aurora Read Replicas do not replicate disk blocks. Replica lag is typically under 15 milliseconds!

Targeted explanations of database replication mechanics, distributed consensus quorums, and NoSQL partitioning.

Q1 Detail the architectural differences between an Amazon RDS Multi-AZ Standby and an Amazon RDS Read Replica.

Multi-AZ Standby: Synchronous physical block-level replication strictly for disaster recovery. Does not possess an independent endpoint and cannot serve read traffic. Provides automatic failover via DNS CNAME update in 60-120 seconds with zero data loss (RPO = 0).

Read Replica: Asynchronous logical engine replication intended for read scaling and reporting. Has its own distinct DNS endpoint and can serve read queries (up to 15 replicas). Subject to replication lag; if promoted to a standalone database, failover is manual and may incur data loss.

Q2 Explain the 4-of-6 storage write quorum mechanism in Amazon Aurora and how it survives Availability Zone failures.

Aurora replicates every 10 GB storage segment 6 ways across 3 Availability Zones (2 copies per AZ). Instead of full-page writes, compute heads transmit lightweight redo log streams.

A write transaction is committed as soon as 4 of the 6 storage nodes acknowledge persisting the log. If an entire Availability Zone is completely destroyed (losing 2 copies), 4 copies remain healthy, allowing Aurora to maintain continuous read and write availability without interruption. Even if a third node fails concurrently (losing 3 of 6), Aurora retains read availability (3-of-6 quorum) and rebuilds missing copies via peer-to-peer gossip.

Q3 What is consistent hashing in Amazon DynamoDB, and why does poor Partition Key selection result in throttling?

DynamoDB hashes the Partition Key value using an internal cryptographic hash function to assign items to physical storage partitions. Each partition is allocated a slice of the table's total provisioned RCU/WCU capacity (up to 1,000 WCUs and 3,000 RCUs per partition).

If an application uses a low-cardinality key (e.g. `country = "US"`), all incoming traffic hashes to the same single physical partition ("hot partition"). When requests exceed that partition's 1,000 WCU limit, DynamoDB throttles requests (`ProvisionedThroughputExceededException`), even if the overall table capacity is 90% idle!

Q4 Contrast Amazon ElastiCache for Redis and Amazon ElastiCache for Memcached from a feature and operational standpoint.

Redis: Supports rich in-memory data structures (Hashes, Sorted Sets, Lists, Bitmaps), disk persistence (RDB snapshots to S3, AOF), Pub/Sub messaging, geospatial queries, and Multi-AZ replication with automatic failover. Single-threaded execution core.

Memcached: Simple, high-throughput in-memory key-value cache. Entirely volatile with zero persistence or replication. Multi-threaded architecture that scales horizontally across large multi-core CPU instances. Ideal for caching simple HTML fragments and JSON strings.

Q5 How does Amazon Redshift's Massively Parallel Processing (MPP) architecture execute analytical queries across petabyte datasets?

A Redshift cluster consists of a Leader Node and multiple Compute Nodes. The Leader Node parses incoming SQL queries, compiles optimized C++ execution code, and distributes query execution slices across compute nodes.

Each compute node has dedicated CPU, memory, and columnar storage slices. Data is distributed across nodes using distribution styles (`KEY`, `ALL`, `EVEN`). When a query executes, all compute nodes process their local columnar data slices simultaneously in parallel, streaming intermediate aggregates back to the Leader Node to produce the final result in seconds.

Scenario 01 Database Failover Triage: Stale DNS Caching Causing 15-Minute Outage Following RDS Multi-AZ Failover

Incident Description: An Amazon RDS PostgreSQL database in `us-east-1a` suffers a hardware host failure. AWS automatically initiates a Multi-AZ failover, successfully promoting the standby in `us-east-1b` in 75 seconds. However, web application servers continue attempting to connect to the dead IP address in `us-east-1a` for over 15 minutes, causing thousands of database connection failures!

Root Cause Analysis & Resolution:

  1. The JVM DNS Caching Trap: When RDS performs a failover, it flips the canonical DNS CNAME record (e.g. `prod-db.xxxx.us-east-1.rds.amazonaws.com`) to point to the new standby's IP address. AWS sets the Route 53 DNS Time-to-Live (TTL) to 5 seconds.
  2. The Java Network Address Cache Flaw: By default, the Java Virtual Machine (JVM) caches DNS lookups forever (`networkaddress.cache.ttl = -1`) to protect against DNS spoofing. Even though Route 53 updated the DNS mapping within seconds, the Java application servers never queried DNS again, stubbornly attempting to connect to the dead IP address!
  3. Remediation: Modify the JVM security configuration (`java.security` or runtime parameter):
    networkaddress.cache.ttl = 5
    This forces the JVM to obey the 5-second TTL, ensuring application connection pools seamlessly reconnect to the promoted database within seconds of an RDS failover.
Scenario 02 NoSQL Partition Hot-Spotting: Resolving IoT Fleet Throttling in Amazon DynamoDB

Incident Description: A smart meter IoT network with 500,000 devices transmits telemetry readings every minute. The DynamoDB table has 10,000 WCUs provisioned. The table schema uses `Date` (e.g. `2026-10-27`) as the Partition Key and `DeviceID` as the Sort Key. During peak morning hours, devices experience heavy `ProvisionedThroughputExceededException` throttles, even though CloudWatch reports total consumed WCUs never exceed 1,500 WCUs (15% utilization)!

Root Cause & Sharding Solution:

  • The Hot Partition Bottleneck: Because all 500,000 devices send readings on the same calendar day, all 10,000 writes/second hash to the exact same single physical storage partition! A single DynamoDB partition is strictly capped at 1,000 WCUs. The remaining 9,000 provisioned WCUs allocated across other idle partitions are completely wasted.
  • Architectural Fix 1 (Inverted Key Hierarchy): Swap the primary key design: make `DeviceID` the Partition Key and `Timestamp` the Sort Key. Because 500,000 distinct device IDs exist, writes distribute evenly across hundreds of physical partitions, scaling throughput linearly.
  • Architectural Fix 2 (Write Sharding / Salt Suffix): If querying by date is strictly mandatory, append a randomized calculated suffix (e.g. `2026-10-27_0` through `2026-10-27_19`) to distribute the date across 20 distinct partition hash buckets.

Engineering Challenge: A cybersecurity operations center stores 100 TB of raw JSON firewall logs monthly in Amazon S3. Scenario 04 In-Memory Cache Thundering Herd: Cache Stampede Mitigation in High-Traffic News Portal

Incident Description: A breaking news portal caches its homepage article data in Amazon ElastiCache for Redis with a 15-minute TTL. At 10:15 AM, the cache key expires. Within 500 milliseconds, 50,000 concurrent web requests experience a cache miss and simultaneously query the backend Amazon Aurora database, triggering a massive CPU spike (100%), exhausting database connection pools, and knocking the site offline.

Cache Stampede (Thundering Herd) Mitigation Strategies:

  • 1. Mutual Exclusion Locks (Distributed Mutex): When a cache miss occurs, the first application worker thread acquires an atomic lock in Redis (`SET lock_key true NX EX 10`).   • 2. Probabilistic Early Expiration (XFetch Algorithm): Instead of waiting for hard expiration, application threads probabilistically refresh the cache entry a few seconds before the TTL expires, based on compute time and read frequency. Background refresh ensures the key is never allowed to expire in production.

46. AWS Identity & Access Management (IAM): Roles, Policies & Least Privilege

AWS IAM provides fine-grained access control across all AWS resources, evaluating cryptographic authorization policies to authenticate principals and enforce the principle of least privilege.

The IAM Policy Evaluation Logic Hierarchy

When an API call is made, IAM evaluates authorization using a strict priority order:
1. Explicit Deny: If any applicable policy (SCP, Permission Boundary, Identity Policy, Resource Policy) contains an `Effect: "Deny"`, the request is immediately denied. An explicit deny overrides all allows!
2. Service Control Policy (SCP): Organizations SCP must allow the action.
3. Permissions Boundary: Must permit the action if attached to the identity.
4. Explicit Allow: At least one identity-based policy or resource-based policy must explicitly grant `Effect: "Allow"`.
5. Default Deny (Implicit Deny): If no explicit allow matches, the request is denied by default.

47. Cryptographic Governance: AWS KMS Envelope Encryption & AWS CloudHSM

Protecting data at rest across hyperscale object, block, and relational datastores relies on hardware-validated cryptographic key hierarchies and envelope encryption algorithms.

Cryptographic Mechanics: The 2-Tier Envelope Encryption Model

Encrypting large multi-gigabyte files directly with a master key over an API would introduce massive network latency and risk key exposure. AWS KMS utilizes Envelope Encryption:

  1. Data Encryption Key (DEK) Generation: The application calls `kms:GenerateDataKey`. KMS uses the root AWS KMS Key (KMS Master Key) inside a hardware security module (HSM) to generate a unique plaintext 256-bit symmetric AES key (DEK) and an encrypted copy of that DEK.
  2. Local High-Speed Encryption: The application uses the plaintext DEK in memory to encrypt the file locally at full memory bus speeds.
  3. Plaintext DEK Destruction: As soon as encryption completes, the application erases the plaintext DEK from memory!
  4. Ciphertext Bundling: The application stores the encrypted DEK as metadata alongside the ciphertext file. To decrypt later, the application sends the encrypted DEK back to KMS (`kms:Decrypt`), which returns the plaintext key to decrypt the payload. The root KMS Key never leaves the physical HSM hardware!

Q1 Explain the step-by-step cryptographic workflow of AWS KMS Envelope Encryption.

1. The application requests a data key from KMS: `GenerateDataKey(KMSKeyId)`.
2. KMS uses the hardware-protected KMS Master Key inside the HSM to generate a plaintext Data Encryption Key (DEK) and an encrypted copy of that DEK.
3. KMS returns both the plaintext DEK and the encrypted DEK to the client over TLS.
4. The application uses the plaintext DEK to encrypt data locally using AES-GCM at memory bus speeds.
5. The application immediately zeroes out the plaintext DEK from RAM.
6. The encrypted DEK is stored as metadata alongside the ciphertext. To decrypt later, the encrypted DEK is sent to KMS (`kms:Decrypt`), which returns the plaintext key to decrypt the payload.

Q2 Detail the complete IAM policy evaluation logic: Explicit Deny, SCPs, Permission Boundaries, and Explicit Allow.

Every authorization decision begins with a Default Deny. The evaluation engine applies the following order:
• 1. Explicit Deny: If any policy (Identity, Resource, SCP, Boundary) contains an explicit Deny, the request is immediately denied.
• 2. Organizations SCP: If the account belongs to an AWS Organization, the Service Control Policy must permit the action.
• 3. Permission Boundary: If attached, the boundary must allow the action.
• 4. Session Policy: If assuming a temporary STS role, session policies must allow the action.
• 5. Explicit Allow: An identity-based policy or resource policy must explicitly permit the action. If all checks pass, the decision is Allow; otherwise, it defaults to Deny.

Q3 Contrast Amazon CloudWatch and AWS CloudTrail from an architectural and operational perspective.

Amazon CloudWatch: System performance and telemetry monitoring service. Collects numeric metrics (CPU, disk IOPS, network bytes) and text log streams. Evaluates alarms to trigger operational actions (Auto Scaling, SNS notifications, EC2 reboot). Focus: "How are my resources performing?"

AWS CloudTrail: Governance and compliance audit trail service. Records cryptographic event records of every administrative and programmatic API call made in the account. Captures the exact IAM identity, timestamp, source IP address, user agent, and request parameters. Focus: "Who modified my cloud resources, when, and from where?"

Q4 Differentiate AWS WAF and AWS Shield regarding OSI layer protection and threat models.

AWS WAF (Layer 7): Web Application Firewall inspecting application payloads (HTTP/HTTPS). Filters SQL Injection, Cross-Site Scripting (XSS), rate-limits brute-force login attempts, and blocks malicious web crawlers. Deployed on ALBs, CloudFront, and API Gateways.

AWS Shield (Layer 3 & 4): Distributed Denial of Service (DDoS) protection. Shield Standard is automatically active on all edge endpoints, scrubbing SYN floods, UDP reflection, and DNS amplification attacks. Shield Advanced provides 24/7 access to the DDoS Response Team, automated Layer 7 mitigations, and financial cost protection against scaling charges.

The ALB forwards the HTTP request to the private IP address of an EC2 instance (c6i.2xlarge). Traditional hypervisors (such as legacy Xen) emulate network devices in software, inducing extensive Context Switches and hypervisor traps. The **AWS Nitro System** eliminates this overhead:

  • Nitro Card for VPC: A dedicated ASIC PCIe expansion board intercepts incoming 100 Gbps Ethernet frames. The Nitro ASIC offloads VPC encapsulation, security group state tracking, and network flow hashing in dedicated silicon.
  • SR-IOV Direct Memory Access (DMA): The Nitro Card leverages Single Root I/O Virtualization (SR-IOV) to expose an Elastic Network Adapter (ENA) directly to the guest operating system. The ASIC copies packet data directly into the Linux guest RAM via PCIe Direct Memory Access without waking or notifying the host CPU.
  • Linux Kernel NAPI & Ring Buffers: The ENA driver receives a PCIe MSI-X interrupt, disabling hardware interrupts and entering Linux NAPI (New API) polling mode. Packets are drained from the rx_ring descriptor buffer, wrapped in an sk_buff struct, and passed up the TCP/IP network stack via NET_RX_SOFTIRQ.
  • Socket Read by Application: The Linux epoll subsystem triggers a wake-up event on the file descriptor owned by the Python/FastAPI async worker thread. The worker parses the JSON order object and prepares the database transaction.

Objective: Construct an enterprise VPC (10.0.0.0/16) spanning 2 Availability Zones, containing 2 Public Subnets, 2 Private Subnets, an Internet Gateway (IGW), an Elastic IP, a NAT Gateway, and dedicated route tables.

Terminal • VPC & Subnet Provisioning 
# 1. Create VPC with DNS hostnames enabled
VPC_ID=$(aws ec2 create-vpc --cidr-block 10.0.0.0/16 --query 'Vpc.VpcId' --output text)
aws ec2 modify-vpc-attribute --vpc-id $VPC_ID --enable-dns-hostnames "{\"Value\":true}"

# 2. Create Internet Gateway and attach to VPC
IGW_ID=$(aws ec2 create-internet-gateway --query 'InternetGateway.InternetGatewayId' --output text)
aws ec2 attach-internet-gateway --vpc-id $VPC_ID --internet-gateway-id $IGW_ID

# 3. Create Public Subnet (AZ-1a) and Private Subnet (AZ-1b)
PUB_SUB=$(aws ec2 create-subnet --vpc-id $VPC_ID --cidr-block 10.0.1.0/24 --availability-zone ap-south-1a --query 'Subnet.SubnetId' --output text)
PRIV_SUB=$(aws ec2 create-subnet --vpc-id $VPC_ID --cidr-block 10.0.10.0/24 --availability-zone ap-south-1a --query 'Subnet.SubnetId' --output text)

# 4. Create Public Route Table and add default 0.0.0.0/0 route to IGW
RTB_PUB=$(aws ec2 create-route-table --vpc-id $VPC_ID --query 'RouteTable.RouteTableId' --output text)
aws ec2 create-route --route-table-id $RTB_PUB --destination-cidr-block 0.0.0.0/0 --gateway-id $IGW_ID
aws ec2 associate-route-table --subnet-id $PUB_SUB --route-table-id $RTB_PUB
VIVA VOCE QUESTIONS & EVALUATION CRITERIA
Q1: Why are 5 IP addresses reserved in every AWS VPC subnet?
Answer: AWS reserves 5 IPs per subnet: .0 (Network), .1 (VPC Router), .2 (DNS Resolver / AmazonProvidedDNS), .3 (Future reserve), and .255 (Network broadcast).

Q2: Why must a NAT Gateway always reside in a Public Subnet?
Answer: The NAT Gateway must translate private subnet IP addresses to its own Public Elastic IP to traverse the Internet Gateway. If placed in a private subnet, it lacks an IGW route and cannot reach the Internet.

VIVA VOCE QUESTIONS & EVALUATION CRITERIA
Q1: When does the EC2 UserData script execute, and with what privileges?
Answer: UserData runs only once during the initial first-boot sequence of the instance lifecycle, executed by the cloud-init service with root privileges.

Q2: Why are Security Groups stateful while Network ACLs are stateless?
Answer: Security Groups track connection state in the hypervisor connection tracking table: return traffic for allowed inbound requests is automatically permitted regardless of outbound rules. NACLs evaluate inbound and outbound rules independently.

Application Load Balancer (ALB) and Auto Scaling Group (ASG) High-Availability Setup

Objective: Deploy an Internet-facing Application Load Balancer across two availability zones, configure target group health checks, and launch a dynamic Auto Scaling Group configured with target-tracking scaling policies (Target CPU Utilization = 60%).

Terminal • ALB Target Group & ASG Provisioning 
# 1. Create Target Group with HTTP health check
TG_ARN=$(aws elbv2 create-target-group \
    --name web-app-tg \
    --protocol HTTP \
    --port 80 \
    --vpc-id $VPC_ID \
    --health-check-path / \
    --health-check-interval-seconds 30 \
    --query 'TargetGroups[0].TargetGroupArn' --output text)

# 2. Create Application Load Balancer spanning Public Subnets
ALB_ARN=$(aws elbv2 create-load-balancer \
    --name web-app-alb \
    --subnets $PUB_SUB $PUB_SUB_2 \
    --security-groups $ALB_SG \
    --query 'LoadBalancers[0].LoadBalancerArn' --output text)

# 3. Create HTTP Listener forwarding traffic to Target Group
aws elbv2 create-listener \
    --load-balancer-arn $ALB_ARN \
    --protocol HTTP --port 80 \
    --default-actions Type=forward,TargetGroupArn=$TG_ARN

# 4. Create Launch Template and Auto Scaling Group (Min=2, Desired=2, Max=6)
aws autoscaling create-auto-scaling-group \
    --auto-scaling-group-name web-asg \
    --launch-template LaunchTemplateName=web-template,Version='$Latest' \
    --min-size 2 --max-size 6 --desired-capacity 2 \
    --target-group-arns $TG_ARN \
    --vpc-zone-identifier "$PRIV_SUB,$PRIV_SUB_2" \
    --health-check-type ELB --health-check-grace-period 300
VIVA VOCE QUESTIONS & EVALUATION CRITERIA
Q1: What happens when an ASG instance fails an ELB health check?
Answer: The load balancer stops routing traffic to the unhealthy target. The Auto Scaling Group marks the instance unhealthy, terminates it, and launches a replacement instance to maintain desired capacity.

Q2: Why is health check grace period necessary in an ASG?
Answer: It provides a buffer window (e.g., 300 seconds) allowing newly launched instances to complete bootstrapping, install software, and start services before health check evaluations begin, preventing premature termination.

VIVA VOCE QUESTIONS & EVALUATION CRITERIA
Q1: Why is CloudFront Origin Access Control (OAC) preferred over public S3 buckets?
Answer: OAC ensures the S3 bucket remains entirely private: users cannot bypass CloudFront edge security, WAF filtering, or caching, preventing direct origin scraping and unauthorized bandwidth consumption.

Q2: What is the minimum billable object size and duration for S3 Standard-IA?
Answer: S3 Standard-IA imposes a minimum billable size of 128 KB and a minimum retention duration of 30 days. Objects smaller or deleted earlier incur penalty charges.

Serverless Microservice: AWS Lambda (Python 3.12), Amazon API Gateway & DynamoDB CRUD

Objective: Build a fully serverless REST API that writes and reads items from Amazon DynamoDB, orchestrated via Amazon API Gateway HTTP API and AWS Lambda.

Python 3.12 • AWS Lambda Function Handler
import json
import boto3

dynamodb = boto3.resource('dynamodb')
table = dynamodb.Table('StudentRegistry')

def lambda_handler(event, context):
    http_method = event.get('requestContext', {}).get('http', {}).get('method', 'GET')
    
    if http_method == 'POST':
        body = json.loads(event.get('body', '{}'))
        table.put_item(Item={'student_id': body['id'], 'name': body['name'], 'course': body['course']})
        return {'statusCode': 201, 'body': json.dumps({'message': 'Record persisted successfully'})}
    elif http_method == 'GET':
        response = table.scan(Limit=50)
        return {'statusCode': 200, 'body': json.dumps(response.get('Items', []))}
    
    return {'statusCode': 400, 'body': 'Unsupported HTTP Method'}
